Close the two remaining Critical gaps in Phase 3's verification report: CR-03 (a weight target
created before any weight entry exists persists `direction: undefined`, silently inverting
on-track color/gap logic for loss-direction users) and CR-04 (editing the exercise-proxy's weekly
target retroactively re-judges every historical week against the new target, contradicting D-08
and the 03-03-PLAN.md must-have that editing the target never resets the streak). Also close the
directly-adjacent Warning WR-04 (invalid weekly-target edits fail silently with no user feedback)
since it shares the exact `ExerciseProxyTile.commitEdit` code path being touched for CR-04.

Purpose: These defects, found by the Phase 3 code review and verification pass (03-REVIEW.md,
03-VERIFICATION.md), directly block Success Criteria #1, #2, and #3 — target pace/on-track status
and the exercise streak are both currently wrong or actively contradicting their own documented
design.
Output: A `resolveWeightDirection` backfill resolver wired into the weight-entry save path, and a
`resolveWeekMet` + Dexie v6 `exerciseWeekSnapshots` table that freezes each week's met/unmet
status against the target that was actually in effect at the time.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Weight-entry save path -> target direction backfill | A user-entered numeric weight value flows into a decision that affects on-track color/gap math read by other views. |
| Weekly-target edit -> historical streak data | An edit to a live value must not be able to retroactively rewrite already-frozen historical records. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-15 | Tampering | Target.direction data integrity | high | mitigate | `resolveWeightDirection` backfills a null/undefined direction using `inferDirection` once any weight entry exists, and `useTargetData` persists `null` (never bare `undefined`) for the not-yet-resolvable case — a malformed/unresolved direction can no longer silently invert on-track color/gap math read elsewhere in the app (CR-03). |
| T-03-16 | Tampering | exerciseWeekSnapshots history integrity | high | mitigate | A past week's `met` status is frozen in `db.exerciseWeekSnapshots` once recorded and is never recomputed against a later-edited `weeklyTarget`; only the current, still-open week is rewritten on each load — closes CR-04's retroactive-rewrite bug. |
| T-03-17 | Denial of Service | useExerciseLogData 52-week snapshot lookups | low | mitigate | Snapshot reads are single-row Dexie `.get()` calls per lookback week (bounded to `WEEK_LOOKBACK=52`, same bound as before — T-03-08 carries forward); no new unbounded scans are introduced, and the raw `exerciseLog` query is now skipped entirely for any week that already has a snapshot. |
| T-03-18 | Repudiation (silent data loss) | ExerciseProxyTile invalid weekly-target edit | low | mitigate | `commitEdit` now calls `toast.error(...)` on invalid input instead of silently discarding it (WR-04). |
| T-03-19 | Tampering (XSS) | TargetModal / ExerciseProxyTile numeric inputs rendered back into the DOM | low | accept | Values remain numeric-typed inputs and React text children throughout; no new free-text/HTML rendering surface is added by this plan. |
</threat_model>
