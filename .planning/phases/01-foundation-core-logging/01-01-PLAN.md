  <action>
    Present the following three one-way architectural decisions to the developer and confirm they accept them before proceeding. These decisions cannot be changed after user data exists in IndexedDB without writing a data migration script.

    ONE-WAY DECISION D-15: The database uses SEPARATE Dexie tables per metric — `weights`, `sleepEntries`, `stepEntries`, `waterEntries`, `heartRates`. A unified entries table with a `type` discriminator field is NOT used. Reversing this after Phase 1 data exists requires a Dexie schema migration and rewriting all queries.

    ONE-WAY DECISION D-16: MIXED CARDINALITY per day. Weight and heart rate allow multiple entries per day (auto-increment `id` as primary key, `date` as index). Sleep, steps, and water allow one entry per day (`date` as primary key — upsert with `put()` overwrites). Changing cardinality after data exists corrupts the data model.

    ONE-WAY DECISION D-17: All dates stored as ISO strings. Daily keys use `YYYY-MM-DD` format (e.g., "2026-09-03"). Sleep bedtime and wake time stored as full ISO timestamps (e.g., "2026-09-02T23:00:00"). No Unix epoch numbers. Changing format after data exists requires migrating every row.

    Do NOT proceed to the tracer task until the developer explicitly confirms these decisions are acceptable.
  </action>
  <reversibility rating="one-way">D-15/D-16/D-17 — separate tables, mixed cardinality, and ISO date format are baked into all exported user data; changing them post-Phase 1 requires a migration script and exported JSON format version bump.</reversibility>
